O `change.md` responde duas perguntas: por que essa mudança existe, e o que vai
ser verdade quando ela terminar.

Quem escreve é o agente, quando planeja. Você lê, corrige e aprova antes de
qualquer implementação. O arquivo nasce na abertura do pacote, é relido antes
de cada grupo e completado no fechamento.

Como o raciocínio fica aqui, a mensagem de commit não precisa repetir ele: quem
quiser saber por que algo foi feito assim abre o pacote arquivado.

## O frontmatter

Sete chaves. Chave sem valor é omitida, nunca escrita vazia.

| Chave | O que é |
|---|---|
| `title` | o nome do pacote, pelo resultado que ele entrega |
| `description` | uma linha, para a lista de arquivados se ler sem abrir nada |
| `changepack` | a versão que planejou |
| `opened` | o dia em que abriu |
| `opened-by` | quem abriu: nome e email do git, os mesmos do commit de abertura |
| `issue` | de onde o trabalho veio, quando veio de algum lugar |
| `shipped` | a versão em que saiu, preenchida no fechamento |

## As seções

O corpo tem dez seções, e nem toda mudança usa todas.

| Seção | O que vai nela |
|---|---|
| Context | o que é verdade hoje, e por que isso é um problema |
| Goal | o comportamento que tem que existir no fechamento |
| Changes | [o desenho](#o-desenho) do que se move |
| Open decisions | as perguntas no caminho, com alternativas e custos |
| Decided | as que já foram respondidas, e o que a outra opção custaria |
| Scope | no que a mudança mexe, e o que ficou de fora |
| Cost | o que continua funcionando, e o que um revert não desfaz |
| Success criteria | o que dá para conferir no fechamento olhando o comportamento |
| Outcome | o que saiu, o que mudou no caminho, o que ficou |
| [Surprises](#surprises) | uma linha por grupo cujo diff não bateu com o desenho |

O template é um piso. Uma seção entra quando o trabalho tem o que dizer nela, e
não para preencher a página.

## O desenho

É a seção Changes, e ela é escrita para você. O desenho vai se formando
enquanto o agente planeja, e é a última coisa que ele escreve, depois de
entender a mudança. Do seu lado é a primeira que você lê: dá para validar o
raciocínio olhando, em vez de ler parágrafos.

O desenho mostra só o que se move. A notação depende do que está mudando. As
quatro abaixo desenham a mesma mudança: a tabela de usuários passa a exigir
confirmação de email.

<Tabs>
<TabItem label="Árvore">

Para arquivos, módulos e pacotes. `+` entrou, `-` saiu, `~` mudou, com um
comentário onde o nome não basta.

```text
+ src/mail/verificacao.ts      o email e o token
~ src/models/user.ts           o campo novo, e o metodo confirmado()
~ src/routes/signup.ts         dispara o email depois de criar
- src/routes/ativar.ts         o /verify entra no lugar
```

</TabItem>
<TabItem label="Tabela">

Para uma coleção, uma tabela, um campo, um estado. Uma linha por coisa que se
move, e no que ela vira.

| Coluna | Hoje | Depois |
|---|---|---|
| `email` | texto, único | igual |
| `verified_at` | não existe | data, nula até a confirmação |
| `status` | `ativo` ou `bloqueado` | ganha `pendente`, que é o novo padrão |

</TabItem>
<TabItem label="Sequência">

Para uma rota, um stream, uma ordem no tempo. Quem chama quem, e nessa ordem.

```text
usuário            api                fila de email
   |  POST /signup  |                      |
   |--------------->|                      |
   |                |  cria com verified_at nulo
   |                |--------------------->|
   |  GET /verify?token=...                |
   |--------------->|                      |
   |                |  grava verified_at, status vira ativo
```

</TabItem>
<TabItem label="Fluxo">

Para um serviço, um deploy, um roteamento. O que roda, e onde para.

```text
login
  |
  v
verified_at nulo? ---> sim ---> 403, e reenvia o email
  |
  não
  |
  v
sessão criada
```

</TabItem>
</Tabs>

A maioria das mudanças usa duas dessas. A árvore e a tabela têm preferência:
elas se leem no terminal, na forge e no editor sem instalar nada.

Embaixo do desenho vai só o que ele não mostra: por que essa forma e não outra.
O desenho não é redescrito em prosa.

Se nada estrutural se move, não tem desenho. E provavelmente não precisava de
pacote.

## As decisões

Uma decisão em aberto entra em Open decisions: a pergunta em negrito, as
alternativas e seus custos numa tabela, e a recomendação em prosa embaixo. Se
nenhuma task começa sem a resposta, ela é marcada como bloqueante, e os grupos
que ela segura também. Você responde; quem marca é o agente.

Decisão respondida vai para Decided, e não é apagada. Fica registrado o que foi
escolhido e o que a outra opção teria custado, para ninguém precisar
reconstruir isso depois.

## Surprises

O desenho diz no que a mudança ia mexer. Enquanto os grupos aterrissam, o diff
de cada um é comparado com ele, e quando os dois discordam uma linha entra em
Surprises, na hora.

Não é lista de bug nem desculpa. É o registro de onde o plano e a realidade se
afastaram, escrito enquanto está fresco em vez de reconstruído no fechamento.
Um grupo que bateu com o desenho não escreve nada, e silêncio é o resultado
comum.

No fechamento, a seção some se ninguém escreveu nada nela. Se tem linhas, elas
ficam no pacote arquivado, que é onde alguém procura quando o código não se
parece com o plano.

## No fechamento

O Outcome é escrito ali: o que saiu, o que mudou no caminho e o que ficou para
depois. Se o pacote foi abandonado, é aqui que isso é dito, junto com o que foi
construído e o que precisaria ser verdade para o trabalho voltar.
