## O que é uma change

Uma pasta no seu repositório, no git, ao lado do código que ela muda. Seu
agente escreve, você aprova, e aí ela roda.

```text
changes/active/stripe-integration/
  change.md        o problema, o objetivo, as decisões, o que se move
  tasks.md         os task groups, e o que prova cada um
  spec-delta.md    as regras que essa change torna normativas, quando torna
```

Ela abre quando o trabalho começa e é arquivada, com data, quando o trabalho
termina. Você nunca escreve esses arquivos. O agente propõe a partir da
conversa que vocês já estavam tendo, e nada entra antes de você dizer sim.

Uma change é maior que uma task comum e menor que um épico. Um épico são várias
changes, quase sempre abertas ao mesmo tempo. Não tem banco e não tem serviço
atrás de nada disso, então qualquer agente que saiba ler uma pasta roda uma.

## Instalação

```bash
npx changepack
```

Ele copia markdown para `.claude/skills/` e escreve um arquivo que é seu. Sua
árvore de dependências não se mexe, e nada fica rodando no seu repositório
depois disso.

Hoje ele chega como uma skill do Claude Code. O procedimento é markdown e a
unidade é uma pasta no seu repositório, então nenhum dos dois está preso a um
agente só.

## Não tem nada para aprender

Nenhum comando para decorar, nenhuma flag, nenhum template para preencher. Não
tem interface para aprender porque não tem interface: o produto inteiro é uma
conversa e uma pasta. Você fala do jeito que já fala, e o procedimento
classifica o que você disse e toma a rota que serve.

| Você fala | Ele faz |
|---|---|
| "implementa a integração com a Stripe" | Classifica como grande demais para uma passada, pergunta antes de abrir qualquer coisa, escreve a change, comita e para antes de implementar |
| "vamos refatorar a tela de configurações em outra branch" | O mesmo, na branch que você disse. A change é uma pasta no repositório, então acompanha a branch em que foi aberta |
| "vamos migrar o sistema" | Divide. Várias changes abertas ao mesmo tempo, cada uma uma unidade que roda, se revisa e se fecha sozinha |
| "pega a change de pagamentos e vai até o fim" | Despacha um agente novo por task group, valida cada um por conta própria e comita task group a task group |
| "pega o task group 3" | Implementa aquele task group e marca cada item conforme a validação dele passa |
| "centraliza essa div" | Diz que isso não precisa de uma change, e centraliza a div |

## O gate

> Nunca abra uma change porque o trabalho mexe em comportamento.
> Abra uma porque uma passada só não dá conta.

## Seus tokens duram

Isso nasceu porque eles não duravam. Uma sessão longa paga pelo histórico
inteiro a cada turno, e poucas sessões comiam um orçamento que era para durar
bem mais.

Um turno carrega entre 4k e 8k caracteres de procedimento: o arquivo que fica
sempre residente, mais a única rota que o trabalho toma. Os dois são presos a
3600 caracteres por um check que roda em todo commit, então o teto é fato e não
intenção.

Rodar uma change inteira despacha um agente novo por task group e guarda quatro
linhas de cada um: os arquivos que tocou, a validação, uma nota para a frente,
e se travou. Todo o resto é descartado. A conversa que roda uma change de dez
task groups tem mais ou menos o tamanho da que roda um só.

## A implementação deixa de ser o trabalho

Mande rodar uma change até o fim e a implementação costuma levar um quarto de
hora. Um task group sozinho leva minutos.

O planejamento não, e nem deveria. Ele pode levar um dia, ou uma conversa
espalhada por vários, e é trabalho a dois: você decide, a change registra o que
você decidiu, e o procedimento para no instante em que encontra uma decisão que
você ainda não tomou.

Essa proporção é o produto. A digitação encolhe, e o que sobra é a decisão, que
sempre foi a parte que era sua.

## Um harness para o seu harness

Os mesmos três arquivos que organizam uma migração de banco organizam a
reescrita do seu `AGENTS.md`, do seu diretório `.claude/`, ou de uma spec
espalhada por quarenta arquivos markdown que se referenciam.

O `spec-delta.md` é o mecanismo. Ele nomeia cada regra que a change adiciona,
altera ou remove, embaixo do documento em que cada uma cai, e se dobra nesses
documentos no fechamento. Nada normativo é escrito antes de o comportamento
existir, e nada se desencontra, porque o delta é o registro do que passou a
valer.

Este repositório é a prova. O changepack é planejado, rodado e fechado pelo
changepack, e toda pasta em `changes/archive/` é uma change no procedimento,
feita pelo procedimento.

## O que não tem aqui

**Não é uma máquina de vibe coding.** Tudo aqui foi desenhado para ser
acompanhado de perto. Você aprova a change antes de uma linha ser escrita, o
working tree continua sendo a superfície de revisão, todo task group comita
sozinho, e o procedimento para no instante em que encontra uma decisão que é
sua. Você deixa o agente trabalhar. Você não deixa ele decidir.

**Nenhuma dependência no seu repositório.** `npx` é um canal, não um runtime.
Um projeto Python, Rust ou Go não ganha manifesto, nem lockfile, nem árvore
instalada.

**Nenhuma CLI onde ele roda.** Nada é instalado onde o changepack trabalha. O
estado é o repositório, que é também por que não tem nada para telefonar para
casa.

**Nenhum serviço, nenhum hook, nenhum daemon.** Uma requisição ao registro do
npm, em um momento só, é tudo que alcança a rede, e uma linha em um arquivo que
é seu guarda a resposta.

**Um working tree só, por padrão.** O working tree é a superfície de revisão,
então uma change não abre branch por conta própria. Peça uma branch ou uma
worktree e ele trabalha lá como em qualquer outro lugar.
