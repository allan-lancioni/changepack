## O que é uma change

Uma pasta no seu repositório, ao lado do código que ela muda.

```text
changes/active/stripe-integration/
  change.md        o problema, o objetivo, as decisões e o desenho do
                   estado desejado
  tasks.md         os grupos de tasks e suas validações, preenchidos em
                   tempo real
  spec-delta.md    as regras que essa change altera, quando altera
```

Ela abre quando o trabalho começa. É arquivada, com a data, quando o trabalho
termina.

## Instalação

```bash
npx changepack
```

Markdown copiado para `.claude/skills/`, mais um arquivo que é seu. Nada entra
nas suas dependências, e nada fica rodando depois.

Hoje ele chega como uma skill do Claude Code. O procedimento é markdown e a
unidade é uma pasta, então nenhum dos dois está preso a um agente só.

## Como você usa

<Steps>

1. Abra uma sessão do Claude Code, como sempre.

2. Discuta a mudança com o agente, refinando pelo tempo que precisar.

3. Quando estiver definido, diga "abra uma change".

4. O agente monta os arquivos. Você revisa.

5. Diga "pode começar". Ou abra uma sessão nova e diga "pega a change X".

6. O agente trabalha e commita por grupo de tasks, parando quando precisa de
   uma decisão sua.

7. Você aprova o que foi feito. A change fecha e vai para o arquivo.

</Steps>

Você não escreve esses arquivos nem decora nenhum comando. Só linguagem
natural. Seu trabalho é decidir e planejar. O agente executa.

Sem framework. Ele pluga em repositório que já existe, e sai com a mesma
facilidade.

## O gate

Se for grande demais, o agente propõe mais de uma change. Se for pequena
demais, ele faz direto, sem change nenhuma.

```text
uma passada resolve?       sim  ->  ele faz e te conta
                           não  ->  ele propõe uma change
grande demais para uma?    sim  ->  ele propõe várias
```

> Nunca abra uma change porque o trabalho mexe em comportamento.
> Abra uma porque uma passada só não dá conta.

## Você fala, ele faz

| Você fala | Ele faz |
|---|---|
| "implementa a integração com a Stripe" | Grande demais para uma passada. Ele pergunta, escreve a change, comita e para antes de implementar |
| "vamos refatorar a tela de configurações em outra branch" | O mesmo, na branch que você disse. Uma change é uma pasta, então acompanha a branch |
| "vamos migrar o sistema" | Divide. Várias changes abertas ao mesmo tempo, cada uma rodada, revisada e fechada sozinha |
| "pega a change de pagamentos e vai até o fim" | Um agente novo por grupo de tasks. Ele valida cada um e comita conforme anda |
| "pega o grupo 3" | Roda aquele grupo, marcando cada item conforme a validação passa |
| "centraliza essa div" | Diz que não precisa de change, e centraliza a div |

## Seus tokens duram

Isso existe porque os meus não duravam. Uma sessão longa paga pelo histórico
inteiro a cada turno.

```text
sempre carregado    SKILL.md            3401 de 3600 caracteres
por turno           uma rota, só uma    3497 de 3600 no pior caso
total por turno     4k a 8k
```

Um check segura os dois tetos em todo commit.

Rodar uma change inteira dá um agente novo para cada grupo de tasks. Voltam
quatro linhas, e todo o resto é jogado fora:

```text
FILES:              o que ele tocou
VALIDATION:         o comando, e passou ou falhou
FOR NEXT GROUP:     no máximo duas frases
BLOCKED:            não, ou a decisão que trava
```

Uma change de dez grupos custa mais ou menos o que custa uma de um grupo.

## A implementação deixa de ser o trabalho

Mande rodar uma change até o fim e a implementação costuma levar um quarto de
hora. Um grupo de tasks sozinho leva minutos.

O planejamento não, e nem deveria. Pode levar um dia, ou vários. Você decide, a
change registra o que você decidiu, e o agente para no instante em que esbarra
numa decisão que você ainda não tomou.

Essa é a troca. A digitação encolhe, e o que sobra é a decisão.

## Um harness para o seu harness

Os mesmos três arquivos funcionam em prosa. A reescrita do seu `AGENTS.md`, do
seu diretório `.claude/`, ou de uma spec espalhada por quarenta arquivos
markdown que se referenciam.

O `spec-delta.md` é o como. Ele lista o que a change faz com cada documento:

```text
+ uma regra que essa change adiciona
~ uma regra que essa change altera
- uma regra que essa change remove
```

No fechamento essas regras entram nos documentos a que pertencem. Nada é
escrito lá antes de o comportamento existir.

Este repositório é a prova. O changepack é planejado, rodado e fechado pelo
changepack.

## O que não tem aqui

**Não é uma máquina de vibe coding.** Foi feito para ser acompanhado de perto.
Você aprova a change antes de uma linha ser escrita. Todo grupo de tasks
commita sozinho. Ele para sempre que a decisão é sua. O agente faz o trabalho.
Você decide.

**Nada nas suas dependências.** `npx` é como ele chega, não onde ele roda. Um
projeto Python, Rust ou Go não ganha manifesto, nem lockfile, nem árvore
instalada.

**Nenhuma CLI, nenhum serviço, nenhum daemon.** Uma requisição ao registro do
npm, uma vez, para perguntar se existe versão nova. É tudo que toca a rede.

**Um working tree só, por padrão.** É no tree que você revisa, então uma change
não abre branch por conta própria. Peça uma branch ou uma worktree e ele
trabalha lá.
