## The unit is a folder

A change package is one unit of planned work: the problem, the behavior it
should produce, and the task groups that get there. It opens when the work
starts, and it is archived, dated, when the work is done.

Three files, all markdown. `change.md` holds the problem, the goal, the
decisions and a drawing of what moves. `tasks.md` holds the task groups, each
with the observation that proves it. `spec-delta.md` holds the rules the change
makes normative, and only when it makes any.

A change package is bigger than a regular task and smaller than an epic. An
epic is several of them, often open at the same time.

It lives in your repository, in git, next to the code it changes. There is no
database and no service, so an agent that can read a folder can run one.

## Install

```bash
npx changepack
```

It copies markdown into `.claude/skills/` and writes one file you own. Your
dependency tree does not move, and nothing runs in your repository afterwards.

It ships as a Claude Code skill today. The procedure is markdown and the unit
is a folder in your repository, so neither is bound to one agent.

## There is nothing to learn

No command to memorise, no flag, no template to fill. You talk the way you
already talk, and the procedure classifies what you said and takes the route
that fits.

| You say | It does |
|---|---|
| "implement the Stripe integration" | Classifies it as too big for one pass, asks before opening anything, writes the package, commits it, and stops before implementing |
| "let's refactor the settings screen on another branch" | The same, on the branch you named. The package is a folder in the repository, so it follows the branch it was opened on |
| "let's migrate the system" | Splits it. Several packages open at once, each one a unit that can be run, reviewed and closed on its own |
| "take the payments change to the end" | Dispatches a fresh agent per task group, validates every one itself, and commits task group by task group |
| "take task group 3" | Implements that task group, and checks each item as its own validation passes |
| "center a div" | Tells you it does not need a package, and centers the div |

## The gate

> Never open a change package because the work touches behavior.
> Open one because a single pass cannot land it.

## Your tokens last

This was built because they did not. A long session pays for its whole history
on every turn, and a few sessions took a budget that was supposed to last.

A turn loads between 4k and 8k characters of procedure: the file that is always
resident, plus the one route the work takes. Both are held to 3600 characters
by a check that runs on every commit, so the ceiling is a fact and not an
intention.

Running a whole change dispatches a fresh agent per task group and keeps four
lines from each: the files it touched, the validation, one note forward, and
whether it is blocked. Everything else is discarded. The conversation that
drives a ten group change is about as long as the one that drives a single
group.

## The implementation stops being the work

Tell it to run a change to the end and the implementation is often a quarter of
an hour. A single task group is minutes.

The planning is not, and should not be. It can take a day, or a conversation
spread across several, and it is joint work: you decide, the package records
what you decided, and the procedure stops the moment it meets a decision you
have not made.

That ratio is the product. The typing collapses, and what is left is the
deciding, which was always the part that was yours.

## A harness for your harness

The same three files that stage a database migration stage a rewrite of your
`AGENTS.md`, your `.claude/` directory, or a specification spread across forty
markdown files that reference one another.

`spec-delta.md` is the mechanism. It names every rule a change adds, changes or
removes, under the document each one lands in, and folds into those documents
at closure. Nothing normative is written before the behavior exists, and
nothing drifts, because the delta is the record of what became true.

This repository is the proof. changepack is planned, run and closed by
changepack, and every folder under `changes/archive/` is a change to the
procedure, made by the procedure.

## What is not there

**Not a vibe coding machine.** Everything here is built to be watched. You
approve the package before a line is written, the working tree stays the review
surface, every task group commits on its own, and the procedure stops the
moment it meets a decision that is yours. You let the agent do the work. You do
not let it decide.

**No dependency in your repository.** `npx` is a channel, not a runtime. A
Python, Rust or Go project acquires no manifest, no lockfile and no installed
tree.

**No CLI where it runs.** Nothing is installed where changepack works. The
state is the repository, which is also why there is nothing to phone home
about.

**No service, no hook, no daemon.** One request to the npm registry, at one
moment, is everything that reaches the network, and a line in a file you own
remembers the answer.

**One tree, by default.** The working tree is the review surface, so a package
does not open a branch by itself. Ask for a branch or a worktree and it works
there like anything else.
