`change.md` answers two questions: why this change exists, and what will be
true when it is done.

You write it when the package opens, read it again before each group, and
finish it at closure. Because the reasoning lives here, the commit message
does not repeat it: anyone who wants to know why something was done this way
opens the archived package.

## The frontmatter

Seven keys. A key with no value is omitted, never written empty.

| Key | What it is |
|---|---|
| `title` | the package, named for what it delivers |
| `description` | one line, so a list of archived packages reads without opening any |
| `changepack` | the version that planned it |
| `opened` | the day it opened |
| `opened-by` | who opened it: git name and email, the same the opening commit signs with |
| `issue` | where the work came from, when it came from somewhere |
| `shipped` | the release it shipped in, filled at closure |

## The sections

The body has ten sections, and not every change uses all of them.

| Section | What goes in it |
|---|---|
| Context | what is true today, and why that is a problem |
| Goal | the behavior that has to exist at closure |
| Changes | [the drawing](#the-drawing) of what moves |
| Open decisions | the questions in the way, with alternatives and costs |
| Decided | the ones already answered, and what the other option would have cost |
| Scope | what the change touches, and what was left out |
| Cost | what keeps working, and what a revert does not undo |
| Success criteria | what closure can check by looking at behavior |
| Outcome | what shipped, what changed on the way, what was left |
| Surprises | a line per group whose diff did not match the drawing |

The template is a floor. Add a section when the work has something to say in
it, not to fill the page.

## The drawing

This is the Changes section. You write it last, once you understand the
change, and whoever reads the package reads it first.

Draw only what moves. The notation depends on what is changing. The four below
draw the same change: the users table starts requiring email confirmation.

<Tabs>
<TabItem label="Tree">

For files, modules and packages. `+` added, `-` removed, `~` changed, with a
comment where the name is not enough.

```text
+ src/mail/verification.ts     the email and the token
~ src/models/user.ts           the new field, and isConfirmed()
~ src/routes/signup.ts         sends the email after creating
- src/routes/activate.ts       /verify takes its place
```

</TabItem>
<TabItem label="Table">

For a collection, a table, a field, a state. One row per thing that moves, and
what it becomes.

```markdown
| Column | Today | After |
|---|---|---|
| `email` | text, unique | unchanged |
| `verified_at` | does not exist | a date, null until confirmed |
| `status` | `active` or `blocked` | gains `pending`, the new default |
```

</TabItem>
<TabItem label="Sequence">

For a route, a stream, an order in time. Who calls whom, and in what order.

```text
user               api                mail queue
   |  POST /signup  |                     |
   |--------------->|                     |
   |                |  creates with verified_at null
   |                |-------------------->|
   |  GET /verify?token=...               |
   |--------------->|                     |
   |                |  writes verified_at, status becomes active
```

</TabItem>
<TabItem label="Flow">

For a service, a deploy, a routing. What runs, and where it stops.

```text
login
  |
  v
verified_at null? ---> yes ---> 403, and the email is sent again
  |
  no
  |
  v
session created
```

</TabItem>
</Tabs>

Most changes use two of these. Prefer the tree and the table: they read in a
terminal, on a forge and in an editor with nothing installed.

Under the drawing goes only what it does not show, which is why this shape and
not another one. Do not describe the drawing in prose.

If nothing structural moves, there is no drawing. And there probably did not
need to be a package.

While the package runs, each group's diff is compared to this drawing. When the
two disagree, a line goes under Surprises.

## The decisions

An open decision goes under Open decisions: the question in bold, the
alternatives and their costs in a table, and the recommendation in prose below
it. If no task can start without the answer, say it is blocking, and mark the
groups it holds.

An answered decision moves to Decided, and is not deleted. What was chosen and
what the other option would have cost stay on the record, so nobody has to
reconstruct it later.

## At closure

Outcome is written then: what shipped, what changed on the way, and what was
left for later. If the package was dropped, that is said here too, with what
was built and what would have to be true for the work to come back.

Surprises is deleted if nobody wrote anything under it. If there are lines,
they stay.
